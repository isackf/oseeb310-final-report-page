OPERATING SYSTEMS / FINAL PROJECT / DEMONSTRATION

Understanding system activity through log analysis

We examine how recorded system events vary across services and over time, then use a simple screening rule to identify periods worth investigating.

Topic System log analysisTools Python · Pandas · MatplotlibFormat Technical report + code
About this example

The data used here were generated for demonstration. The charts are real outputs of the supplied code, but they do not describe an actual Linux or OpenStack installation. For the course project, each group must analyze a real public dataset and report its own findings.

01 / BACKGROUND

Introduction

System logs provide a record of what services and processes report during operation. They include routine activity as well as warnings and errors. By examining these records over time, we can describe activity patterns and identify intervals that may need closer inspection. We cannot, however, conclude that a system has failed simply because it produced many messages.

RQ 01System activity

Which services produce the most events, and how does activity change over time?

RQ 02Error patterns

When do error-level messages cluster, and can a simple rule prioritize intervals for inspection?

These questions guide the analyses presented below.

Methodology

Rule used to flag high-error periods

An hour is flagged when it contains more than 12 ERROR records. We use this fixed threshold to demonstrate the method; it has not been validated as a failure-detection threshold.

04 / RESULTS

Results and analysis

We organized the results around the two research questions. The first three figures describe overall activity; the final two focus on the timing of error messages and the intervals selected for closer examination.

Which services are most active?

The number of messages differs across the five simulated services. This is useful for describing where logging activity is concentrated, but it does not tell us which service is most reliable. A service that records routine activity frequently can have a higher count without experiencing more faults.

05 / DISCUSSION

Discussion

ACTIVITY

Message volume and service behavior

The event-count plots show differences between services and across time. These differences may reflect service activity, but logging frequency and configuration also affect them. We therefore interpret them as patterns in recorded messages rather than direct measures of reliability.

ERRORS

Error clusters and possible incidents

The error timeline shows why looking only at the total number of errors can hide important temporal patterns. Three hours passed our screening threshold. Because the sample has no independently verified incident labels, we cannot measure detection accuracy or identify the cause of any supposed failure.

LIMITATION

Limits of this demonstration

The synthetic records were designed to make the workflow easy to follow. They are suitable for checking the scripts and the presentation of results, not for drawing conclusions about real systems. An analysis of public logs would require a parser matched to the source format and a careful review of the chosen anomaly threshold.

06 / LESSONS

What we learned

This exercise highlights several practical lessons about log analysis and the interpretation of operating-system activity.

01

Data preparation changes the results

Missing timestamps and inconsistent formats can create misleading hourly trends. Validating the records is as important as plotting them.

02

Counts do not explain causes

Event frequency, severity labels, and threshold flags answer different questions. None of them independently establishes why an event occurred.

03

Link the plots to OS behavior

Understanding services, process activity, and error handling helps decide which patterns are worth investigating.

04

Make the analysis repeatable

Keeping the input format, scripts, dependencies, and chosen threshold documented allows others to reproduce the figures.

07 / CONCLUSION

Conclusion

In this demonstration, log records were used to compare service activity, examine changes over time, and identify three hours with elevated error counts under a fixed screening rule. The analysis shows what can be learned from log summaries, but also where their interpretation stops. Unusual activity is a reason to investigate, not evidence on its own of a system failure.

08 / CODE

Code and reproducibility

The code and sample-data generator are provided in the same repository as this report. With Python 3.10 or later, the following commands regenerate the dataset, the five figures, and a JSON summary.

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python scripts/make_sample.py
python -m src.analyze --input data/sample/illustrative_logs.csv --output docs/figures
python -m unittest discover -s tests -v

On Windows, activate the environment with .venv\Scripts\activate. The CSV reader expects the demonstration format; raw Loghub data require separate parsing.
