OPERATING SYSTEMS / FINAL PROJECT / DEMONSTRATION

What can system logs tell us about operating-system behavior?

An evidence-led investigation of event frequency, temporal patterns, error messages, and potential anomalies—with a reproducible Python workflow.

Topic System log analysisTools Python · Pandas · MatplotlibFormat Technical report + code
Teaching example · not empirical evidence

The dataset and results on this website are synthetic and illustrative. This is an example of how to present a final project, not an analysis of a real Linux or OpenStack system. Student submissions must use a documented public dataset.

01 / PURPOSE

Introduction & research questions

Operating systems and infrastructure services record messages about routine events, warnings, and errors. These records can help investigate system activity and identify periods that deserve attention. However, a high log count or an unusual burst is not proof of a failure.

RQ 01Activity

Which services produce the most events, and how does activity change over time?

RQ 02Abnormal events

When do error-level messages cluster, and can a simple rule prioritize intervals for inspection?

A strong final report makes every plot answer a clearly stated question.

05 / INTERPRETATION

Discussion: what the plots do—and do not—show

FINDING A

Log volume is not service reliability

Counts are shaped by service workload and logging configuration. A highly active service may emit many routine messages without experiencing errors. Cross-service comparisons need this qualification.

FINDING B

Temporal clusters justify investigation, not diagnosis

The error timeline highlights concentrated intervals, and the threshold singles out three demonstration hours. But no verified incident labels are present, so precision, recall, root cause, or real-world fault frequency cannot be inferred.

LIMITATION

The sample contains deliberate artificial patterns

These figures validate the reporting workflow, not the reliability of any operating system. Applying this method to real data requires source-specific parsing, sensitivity checks, and verification against labels when available.

06 / REFLECTION

What we learned

The report should explain technical understanding, not only recount which Python libraries were used. These are examples of the kinds of learning outcomes a team might substantiate:

01

Parsing matters

Bad timestamps or inconsistent message formats can distort apparent trends.

02

Metrics need context

Frequency, severity, and anomalies measure different properties.

03

OS concepts connect to evidence

Service behavior, logging and error handling explain what to investigate.

04

Reproducibility is part of research

A reader should be able to rerun the processing and regenerate plots.

07 / TAKEAWAY

Conclusion

This example illustrates how event counts, time-based aggregation, severity distributions, and rule-based screening can be organized into a coherent operating-systems analysis. The central technical lesson is to separate observed log patterns from verified system failures. A genuine project conclusion should summarize two or three specific, data-supported results from the selected real dataset.
